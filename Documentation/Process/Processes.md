# Process for the Project

## Development Process

For this project, we used an iterative approach with flexible task organization. 
The development was divided into two main stages:

- General Phase (Entire team): We worked together to conduct the in-person requirements gathering with School Control and the initial alignment.

- Specialization Phase (Subgroups): Once the information was collected, we divided the work into two subgroups to optimize time:
[Subgroups Members](../Process/Team-Metric-and-Roles.md)

- Repository and architecture subgroup: Responsible for the GitHub structure, version control, and documentation of requirements.
- Information and video subgroup: Responsible for processing the procedure data, writing content, and preparing the presentation and the video.



## Process Management
The tracking of agreements and tasks was carried out through the following activities and tools:

- Communication and coordination: Synchronous follow-up sessions via Discord calls and WhatsApp messages.

- Key Meetings:

    1. September 25, 2026 (10:00 PM): Team meeting to define the appropriate project approach and analyze the tasks to be carried out.
    2. September 28, 2026 (2:00 PM): In-person interview of the entire team with the School Control staff and the course professor to gather information about procedures, timelines, and frequently asked questions.
    3. September 29, 2026 (9:00 PM): Meeting with another team to unify formats (specifically the functional and non-functional requirements) because they shared the same problem.

- Deliverable tracking: Progress monitoring through the updates uploaded to the GitHub repository.

## GitHub Process
- For the creation of the GitHub repository, a main branch was made, to which information was added a draft in the README.md file, folders with empty files for the requirements information, and collaborators.
- For development, an Issue is created with the description of what will be done, in order to create a new branch, in which the commits for the issue will be worked on within VS Code; Once finished, a PR is made to the GitHub repository, the collaborators review it looking for errors, changes, or possible improvements (we coordinate on this via WhatsApp); if it is definitive, a merge to main is done; if not, it is rejected and the necessary adjustments or changes are made to create a new PR.
